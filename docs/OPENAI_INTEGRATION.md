# OPENAI_INTEGRATION.md

## Purpose

This document explains the optional OpenAI integration that landed in the snapshot-first Phase 7 pass. It is intentionally narrow, privacy-aware, and bounded.

## Core rules

The current design is built around these invariants:

- the OpenAI provider is optional and opt-in
- the model never reads the live SQLite database directly
- the only outbound artifact is a local snapshot generated by `ringmaster snapshot export`
- `redacted` is the default privacy profile
- requests are stateless by default
- no OpenAI tools are enabled by default
- no web search, file search, or remote retrieval are enabled in this pass
- there is no freeform chat surface and no prompt textbox in the TUI

## Commands

Canonical commands:

```bash
cargo run -- snapshot export --demo --profile redacted --out /tmp/ringmaster-snapshot.json
cargo run -- ai review /tmp/ringmaster-snapshot.json --dry-run
cargo run -- ai compare /tmp/ringmaster-snapshot.json /tmp/ringmaster-snapshot.json --dry-run
```

## Snapshot-first design

The product uses a strict two-step flow:

1. export a snapshot from local persisted data
2. analyze that snapshot through a provider boundary

This keeps the privacy boundary inspectable and testable. It also means:

- AI runs can be reproduced from a saved artifact
- snapshot exports remain useful even when AI is disabled
- the user can see exactly which file would leave the machine

## What is sent

When a real OpenAI call is enabled and the user runs `ai review` or `ai compare`, the provider sends:

- the compact JSON snapshot artifact for review
- the compact JSON snapshot artifacts for compare
- stable system instructions
- a strict JSON Schema contract for the output
- optional provider metadata such as reasoning effort or `safety_identifier`

## What is not sent

The current pass does not send:

- the live database
- refresh tokens
- access tokens
- config files
- webhook secrets
- callback URLs and auth internals in the default redacted profile
- arbitrary freeform user prompts
- OpenAI tool definitions
- browsing or remote retrieval instructions

## Privacy profiles

### `redacted`

Default export mode.

Behavior:

- removes obvious personal/account identifiers
- minimizes free-text leakage
- strips review-signal free text by default
- keeps metrics, trends, freshness, capabilities, and local follow-up references useful

### `balanced`

Middle-ground mode.

Behavior:

- preserves the same overall privacy posture
- allows richer derived labels where safe
- still avoids sending secrets or config/auth internals

### `full`

Highest-detail export mode.

Behavior:

- keeps more local explanatory text when available
- still does not include secrets, tokens, or auth/config internals
- should be used only when the user explicitly wants the broader export

## Provider seam

The provider boundary currently has three implementations:

- `dry_run`
- `fixture`
- `openai`

This keeps the rest of the product from depending directly on OpenAI-specific behavior.

## Structured outputs

The OpenAI path uses the Responses API with strict Structured Outputs.

Current artifact contracts:

- `ReviewArtifactV1`
- `CompareArtifactV1`

Important consequences:

- the app does not parse prose blobs
- the local renderer turns structured JSON into the readable briefing
- schema drift can be tested directly

## Stateless mode

The default provider mode is stateless.

Current default behavior:

- `store: false`
- no chat history retained by the API on behalf of the app
- no stateful conversation thread in this pass

If stateful mode is enabled later through config, that will be a deliberate opt-in change and must not become the silent default.

## Prompt and schema versioning

The app persists prompt and schema versions with every AI artifact.

Current versions:

- snapshot schema: `ringmaster.snapshot.v1`
- review output schema: `ringmaster.ai.review.v1`
- compare output schema: `ringmaster.ai.compare.v1`
- review prompt: `review_prompt_v1`
- compare prompt: `compare_prompt_v1`

Each persisted artifact also records:

- provider
- model
- reasoning effort
- request mode
- input transport
- run mode
- privacy profile
- snapshot hash linkage
- created timestamp

## Dry-run and fixture testing

The OpenAI layer is testable without any real API call.

Supported flows:

- `--dry-run`
- `--fixture <path>`

These modes are the default verification path for local development and CI-style checks.

## Intentional deferrals

This pass does not include:

- freeform chat
- arbitrary natural-language Q&A over the live database
- direct database-to-OpenAI access
- browsing-enabled or tool-enabled OpenAI runs
- file-upload transport for provider input
- a dedicated AI chat screen in the TUI

Those behaviors would expand the privacy and product surface significantly and require a separate design pass.
